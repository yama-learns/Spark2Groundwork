# 工作流憲章（T0）

**文件層級：T0。** 效力次於 `AGENTS.md`，高於其餘一切。

> ⛔ **本檔不得含狀態。** ⛔ **本檔不重述其他文件的規則，只定義流程。**

---

## 1. 拓撲事實（**一切規則的前提**）

| 事實 | 後果 |
|---|---|
| **沒有常駐編排器** | 跨工作段的資訊，只能靠檔案傳遞 |
| **沒有共享記憶** | 「上次說過」在下一個工作段等同不存在 |
| **AI 之間不直接溝通** | 一切交換須落地為檔案，且經過主持人 |
| **主持人是唯一裁決點** | 裁決佇列會成長，須可見化（§5.1） |

⛔ **任何以「對話中提過」「AI 記得」為前提的設計，在這個拓撲下都等於沒有設計。**

## 3. 文件分層（**依更新頻率分，不依主題分**）

| 類 | 更新頻率 | 例 |
|---|---|---|
| **狀態** | 每輪覆寫 | `NEXT_SESSION_MEMO.md` |
| **規格** | 罕有 | T0 兩份、`RULES.md`、`policy/*` |
| **資料** | 事件驅動，只增不改寫 | 台帳、`Incident_Log.md`、`handoffs/` |
| **索引** | 隨檔案增減 | `file_index.md` |

### 3.1 ⛔ 狀態只准出現在狀態類文件

**一份混入狀態的文件，會繼承其最快變動部分的更新頻率，
而讀者分不出哪一段是舊的——每一段單獨讀起來都正常。**

### 3.2 每條規則只有一個定義處

**任何規則、判準、表格，全專案只在一處定義；其餘位置一律「引用，不重述」。**

🔴 **路徑、目錄名、檔名樣式與欄位名同樣是規則，同樣只能有一個定義處。**

⚠️ **重複本身無害，不同步才致命——而不同步是重複的必然結局，不是意外。**
⛔ **一個照著三份互相矛盾的規格之一去做的 agent，沒有判斷失誤；錯的是那三份規格。**

**路徑的唯一定義處是 `scripts/harness/framework_config.py`；
各規則的定義處登錄於 `file_index.md` §0。**

### 3.3 文件增生防線

**新增任何治理文件前，先回答三個問題：**

1. 這件事能不能寫進既有文件的一節？
2. 若不能，是因為主題不同，還是因為**更新頻率不同**？
3. 這份新文件的權威範圍是什麼？**它與既有文件重疊的部分歸誰管？**

⚠️ **精簡不是一次性動作，回彈是預設行為。**

### 3.4 引用格式

| 情形 | 寫法 |
|---|---|
| 本檔 | §N |
| 其他文件 | `` `<檔名>.md` `` §N |

⛔ **不得使用會歧義的簡稱**（例如專案中有兩份「憲章」時單寫「憲章 §N」）。
⛔ **引用失效家族時寫名稱，不寫編號**——**編號是表格的序號，名稱才是識別碼。**
🔴 **一個靜默改指的引用，比一個懸空的引用危險，因為它還是綠的**——而感測器只抓得到後者。
⛔ **引用其他專案的章號時須寫明專案名。**
**繼承規則時連同它的引用一起繼承，是「索引當權威」的一種形態。**

## 4. 儀式（**硬閘門，不可跳過**）

### 4.1 開工

1. **宣告型號**（`policy/MODEL_IDENTITY.md`）
2. 讀狀態文件（`NEXT_SESSION_MEMO.md`）
3. 讀 T0 兩份
4. 首次參與者加讀 `Incident_Log.md`
5. **複述自己的寫入範圍**（§6）
6. 跑 `run_all_sensors.py`，**確認退出碼，並依下表處置**

#### 4.1.1 🔴 退出碼非 0 時怎麼辦

> ⚠️ **一個只有檢查、沒有處置的儀式步驟，實際效果等於沒有這一步。**

| 退出碼 | 處置 |
|---|---|
| **0** | 照常開工 |
| **1（FAIL），且與本輪任務無關** | ✅ 開工，**但須在本輪產出物開頭登錄**：FAIL 幾筆、為什麼判定無關、誰負責清 |
| **1（FAIL），且與本輪任務有關** | ⛔ **先處理，不得開工** |
| **2（INCOMPLETE）** | ⛔ **停止並回報。**「查不了」⛔ 不得預設為「無關」 |

⛔ **判不出屬於哪一種時，一律當成最後一列處理**（§4.3 末列同理）。

### 4.2 收工

1. 跑 `run_all_sensors.py`
2. 覆寫狀態文件
3. **交出交接封包**（`policy/HANDOFF.md`）
4. 提出決策請求（§5）

⚠️ **凡本輪變更影響到他人的權限、規格或工具行為，一律須交封包並指名收件人**——
**包含治理角色本身。否則其他角色只會在下次違規時才發現規則變了。**

---

### 4.3 🔴 當工作指令與 T0 衝突時（**最容易被忽略的一條**）

**「決策請求」是用來提議修改規則的，它不回答「此時此刻我該怎麼辦」。**

> ⚠️ **一個 agent 靠自己推導出「我可以破例」，本身就是這套框架最該擔心的事。**

**→ 明文處置，四選一，依序判斷：**

| 情形 | 處置 |
|---|---|
| 指令與 T0 的**硬禁止**（⛔ 條款）衝突 | ⛔ **停止並回報。不得執行。** |
| 指令與 T0 的**程序規定**衝突，且**不執行就無法完成任務** | ✅ 執行，**但須在產出物開頭登錄豁免**：豁免了哪一條、為什麼、代價是什麼 |
| 指令與 T0 衝突，但**有不衝突的替代做法** | ✅ **一律改走替代做法**，並回報你改了 |
| 無法判斷屬於哪一種 | ⛔ **停止並回報。** ⚠️ 「無法判斷」不得預設為可執行 |

⛔ **不得靜默執行。** 三種可執行的情形都要求你說出來。
**框架能容忍破例，不能容忍沒有人知道破過例。**

## 5. 決策請求標準格式

```
> **[裁決請求 N] <一行標題>**
> **當前變動：** 具體要改什麼
> **動機：** 為什麼現在要改
> **驗證狀態：** 我驗證了什麼、沒驗證什麼、殘餘風險是什麼
> **選項：** [A …]（建議）／[B …]／[C 不處理]
```

⛔ **「驗證狀態」欄不得為空，且不得寫「已充分驗證」。**

### 5.1 待裁決佇列須可見化

狀態文件中的待裁決清單**須含「已等待幾輪」欄**。

⚠️ **理由：** 主持人是唯一裁決點。當佇列成長速度超過消化速度，
**失效形態是「裁決品質下降」而非「裁決沒做」——那不會有任何紅燈。**
**等待輪數本身就是訊號。**

## 6. 寫入範圍

**依所選 profile 設定，登錄於 `file_index.md`。**

### 6.1 什麼是「產出區」

**產出區 ＝ 該角色本輪的工作成果應該落地的目錄。**

| 情境 | 產出區 |
|---|---|
| 單一 AI | 專案根目錄，**扣除**台帳、T0 與 `scripts/` |
| 多角色 | `framework_config.py` 的 `write_scopes` 所列 |

⛔ **無論哪一種情境，下列一律不在任何 AI 的產出區內：**
`ledgers/`（台帳）、`governance/AGENTS.md`、`governance/WORKFLOW_CONSTITUTION.md`

✅ **`NEXT_SESSION_MEMO.md` 是每個角色產出區的一部分**——
收工儀式要求覆寫它（§4.2），若不納入，**§4 與 §6 會互相牴觸**。
⚠️ 此項由框架自身的實測發現：受測 agent 因兩節牴觸而選擇不覆寫，
**該檔至今是三個空格。**

**三條通則：**

1. **一個角色只寫自己的產出區 ＋ `handoffs/`。**
2. **台帳預設不在任何 AI 角色的寫入範圍內**——⚠️ **這是預設值，⛔ 不是禁令。見 §6.3。**
3. **每個例外都要寫下它的代價。**
   ⚠️ 一個豁免是可以的，但**豁免應該是「看得見的」而不是「安靜的」**。


### 6.2 操作性目錄（**它們不是產出區**）

| 目錄 | 是什麼 | 進版本控制 | 被感測器掃描 |
|---|---|---|---|
| `scratch/` | **沙盒。** 為了驗證一個判斷而臨時建立的東西：重現用的小 repo、試跑的腳本、丟棄式的樣本。慣例路徑 `scratch/<主題>_sandbox/` | ⛔ 否 | ⛔ 否 |
| `archive/` | 已退役但**刻意不刪除**的舊版本 | ✅ 是 | ⛔ 否 |
| `_to_delete/` | 在**無法刪檔的環境**中，「已判定該刪」的暫置處 | ⛔ 否 | ⛔ 否 |

🔴 **`scratch/` 的關鍵性質：裡面的東西 ⛔ 不得被引用。**
**沙盒的用途是得到一個結論，不是產生一份可以被別人引用的東西。**
⚠️ **它不進版本控制，所以下一輪的人打開你的引用時，那個檔案已經不在了**——
**而一個指向不存在檔案的引用，在報告上與一個有根據的引用長得一樣。**
→ **要留下的東西，先從 `scratch/` 搬進你的產出區，再引用。**

⚠️ **`_to_delete/` 是環境限制的產物（某些檔案系統拒絕 `unlink`），⛔ 不是垃圾桶。**
⛔ **搬進去之後必須告訴人，由人真正刪除**——**一個沒有人知道的 `_to_delete/`，
與沒有刪掉完全一樣。**

⚠️ ⛔ **`excluded_dirs` 收錄它們是為了省掃描成本，不是為了授權。**
**「不用掃」與「不准動」是兩件事**——見 `scripts/harness/framework_config.py` 該鍵的註解。


### 6.3 🔴 授權由使用者決定，⛔ 不由本框架決定

**使用者可以授權 AI 寫入這個專案裡的任何東西，包含台帳。**
⛔ **本框架沒有立場禁止那件事**——**每個專案由該專案的主持人負責，
而本框架不對任何專案的最終成品承擔責任。**

⚠️ **理由：一條使用者無法解除的禁令，會在他真的需要解除時被整個繞過，
而繞過不會留下紀錄。⛔ 一個能被設定關掉的閘門，比一個被繞過的閘門安全。**

**機械對應物：** `governance_config.json` 的 `deny`。
**清空它，就是完整授權。**

#### 做決定時值得知道的一件事（⛔ 這是資訊，不是規勸）

| | 壞掉之後 |
|---|---|
| **框架文件**（`governance/` `policy/` `profiles/` `prompts/` `scripts/` …） | ✅ **從 GitHub 重新下載覆蓋** |
| **`ledgers/` `corpus/` `corpus_md/` `handoffs/` `incidents/` `PROJECT.md`** | 🔴 **沒有任何地方可以還原** |

**預設的 `deny` 只擋第二類，⛔ 不擋第一類**——治理 Agent 因此可以完整維護治理文件，
**而那正是這套框架能被使用者自己養下去的前提。**

#### ⚠️ 兩件即使完整授權也不會改變的事

1. **AI 仍然要在 `handoffs/` 交出「本輪寫入了哪些檔案」**（`policy/HANDOFF.md` §3.3）。
   **授權改變的是能不能寫，⛔ 不改變寫完要不要說。**
2. `ledgers/Conjecture_Ledger.md` 的 **`反證條件裁決` 欄**仍然 ⛔ 只由人改。
   🔴 **那一欄是「人已經裁決」的唯一記錄——若 AI 可以自己填，裁決權就只是一個字串。**

## 7. 感測器治理

### 7.1 變更三關（缺一不得提交）

① 成對種入缺陷樣本（**「必須抓到」＋「必須不誤報」**）
② `run_selftest.py` 全數通過
③ 於 `scripts/harness/SENSOR_CHANGELOG.md` 登錄觸發個案

### 7.2 「無實測個案不改」的適用範圍

| 對象 | 規則 |
|---|---|
| **感測器** | ⛔ **無實測個案不建。** 誤報會教人忽略感測器 |
| **文件規則** | ✅ 得依風險預先設立，**但須標 `[預測]` 並寫下複核時機** |

⚠️ **兩者的失效成本不對稱，所以判準不該相同：**
**一支誤報的感測器會被關掉，而一條沒被觸發的文件規則只是沒被觸發。**

### 7.3 查核工具誤報的處置

⚠️ **當一個查核工具宣告產物有缺陷時，先假設壞掉的是工具。**

| 步驟 | 動作 |
|---|---|
| 1 | **用第二個獨立工具複核** |
| 2 | 檢查比對兩側的**正規化是否完全對稱**。單側正規化＝自製假陽性 |
| 3 | 檢查正規化的**順序**：先剝結構，後壓縮 |
| 4 | 三步都通過，才可宣告產物有缺陷 |

⛔ **不得以「調鬆判準」作為誤報的處置**——那會同時關掉真陽性。
處置一律是修正比對邏輯，**並補一個「必須不誤報」的成對樣本**。

### 7.4 三個退出碼

| 碼 | 意思 |
|---|---|
| 0 | PASS |
| 1 | FAIL — **確定的缺陷** |
| 2 | **INCOMPLETE — 查不了。⛔ 這不等於通過** |

⚠️ **崩潰算 INCOMPLETE，不算 FAIL**——否則「感測器壞了」會看起來像「文件有問題」，
**而那會讓人去修一份沒問題的文件。**

### 7.5 治理變更的跨層檢查表

**每次治理變更前，逐層自問：這次動到哪一層？它會迫使哪一層跟著改？**

| 層 | 對應 |
|---|---|
| **E** 執行 | 沙盒邊界、暫存區 |
| **T** 工具 | `scripts/` |
| **C** 脈絡 | 文件分層、狀態文件、台帳 |
| **L** 生命週期 | 儀式、交接、決策請求 |
| **O** 可觀測 | git 檢查點、log、可重跑指令 |
| **V** 驗證 | 感測器、成對自測 |
| **G** 治理 | 寫入範圍、倫理閘門、語彙規則 |

⚠️ **跨層連鎖多半不是事前想到的，是感測器當場擋下的。**

## 8. 跨模型對抗審計

**規格見 `governance/Audit_Protocol.md`。本節只定四項不可省略者：**

1. 審計者**與被審者不得為同一模型**
2. 報告須含「**我測了什麼／我沒測什麼**」兩欄，**後者不得為空**
3. 結論的效力範圍**不得超出測試矩陣**
4. ⛔ **審計者不修東西**

## 9. 本憲章不宣稱的事

- ⛔ 它**不保證研究是對的**
- ⛔ 它**不保證感測器全綠代表沒有問題**——綠燈只涵蓋已機械化的環節
- ⛔ 它**不能替代主持人的判斷**，只能讓判斷有東西可依據

## 10. 🔴 治理的成本上限（**本節管的是這套框架自己**）

> **治理是研究的成本，⛔ 不是研究的目的。**
> ⚠️ **當治理工作開始排擠研究的時間與運算資源時，治理就已經失效了**——
> **即使每一份治理文件單獨看都是對的。**

### 10.1 使用者是唯一的稽核者

⛔ **不得要求治理 Agent 對自己的維護工作執行對抗審計**——
**那會使治理開銷倍增，而那些運算資源本來要拿去推進研究。**

⛔ **`governance/Audit_Protocol.md` 管的是「研究產出的審計」，不管「治理維護的稽核」。**

### 10.2 稽核只有三個問題（⛔ 不得增加）

| # | 問題 |
|---|---|
| ① | 這一輪改的東西，**我看得懂它為什麼要改嗎？** |
| ② | 它有沒有動到**我不可還原的資料**（台帳、語料、交接、`PROJECT.md`）？ |
| ③ | **感測器還是綠的嗎？** |

🔴 **⛔ 不得要求稽核者判斷改動「對不對」。**
**那需要與治理 Agent 同等的脈絡，而要求使用者具備那個脈絡，正是排擠效應的來源。**

⚠️ **這三問刻意都能在幾分鐘內回答完。**
**一個要花半小時的稽核流程，實際效果是不做稽核。**

### 10.3 治理 Agent 每輪須回報成本

**在交接封包中寫出：本輪動了幾個檔案、花了幾輪對話。**
⛔ **不是為了考核，是為了讓排擠效應變成一個看得見的數字**——
**一個沒有被量出來的成本，不會有人發現它在成長。**

### 10.4 與 §7 的分工

§7 管的是**改感測器這件事的品質**（三關保留）；**本節管的是要不要花力氣改。**
