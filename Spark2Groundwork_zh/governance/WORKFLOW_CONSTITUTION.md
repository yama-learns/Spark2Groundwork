# 工作流憲章（T0）

**文件層級：T0。** 效力次於 `AGENTS.md`，高於其餘一切。

> ⛔ **本檔不得含狀態。** ⛔ **本檔不重述其他文件的規則，只定義流程。**

---

## 1. 拓撲事實（**一切規則的前提**）

| 事實 | 後果 |
|---|---|
| **沒有常駐編排器** | 跨工作段的資訊，只能靠檔案傳遞 |
| **沒有共享記憶** | 「上次說過」在下一個工作段等同不存在 |
| **AI 之間不直接溝通** | 一切交換須落地為檔案，且經過主持人 |
| **主持人是唯一裁決點** | 裁決佇列會成長，須可見化（§5.1） |

⛔ **任何以「對話中提過」「AI 記得」為前提的設計，在這個拓撲下都等於沒有設計。**

## 3. 文件分層（**依更新頻率分，不依主題分**）

| 類 | 更新頻率 | 例 |
|---|---|---|
| **狀態** | 每輪覆寫 | `NEXT_SESSION_MEMO.md` |
| **規格** | 罕有 | T0 兩份、`RULES.md`、`policy/*` |
| **資料** | 事件驅動，只增不改寫 | 台帳、`Incident_Log.md`、`handoffs/` |
| **索引** | 隨檔案增減 | `file_index.md` |

### 3.1 ⛔ 狀態只准出現在狀態類文件

⚠️ **來源：先行專案的派工文件把待辦寫在自己的 §5，三小時內就出現兩筆「✅ 已完成」還留著。**

> **一份混入狀態的文件，會繼承其最快變動部分的更新頻率。**
> **而讀者不會知道哪一段是舊的——每一段單獨讀起來都正常。**

### 3.2 每條規則只有一個定義處

**任何規則、判準、表格，全專案只在一處定義；其餘位置一律「引用，不重述」。**

⚠️ **實測：某專案曾有 17 條跨檔完全相同的句子。**
**重複本身無害，不同步才致命——而不同步是重複的必然結局，不是意外。**

**各規則的定義處登錄於 `file_index.md` §0。**

### 3.3 文件增生防線

**新增任何治理文件前，先回答三個問題：**

1. 這件事能不能寫進既有文件的一節？
2. 若不能，是因為主題不同，還是因為**更新頻率不同**？
3. 這份新文件的權威範圍是什麼？**它與既有文件重疊的部分歸誰管？**

⚠️ **實測：某專案的治理文件曾自 46 份精簡至 22 份，其後又回彈至 42 份。**
**精簡不是一次性動作，回彈是預設行為。**

### 3.4 引用格式

| 情形 | 寫法 |
|---|---|
| 本檔 | §N |
| 其他文件 | `` `檔名.md` `` §N |

⛔ **不得使用會歧義的簡稱**（例如專案中有兩份「憲章」時單寫「憲章 §N」）。
⛔ **引用其他專案的章號時須寫明專案名**——
⚠️ 先行專案的失效家族表繼承自另一專案時，**連同對方的章號一起繼承，四筆懸空引用長期無人發現**。
**繼承規則時連同它的引用一起繼承，本身就是「索引當權威」的一種形態。**

## 4. 儀式（**硬閘門，不可跳過**）

### 4.1 開工

1. **宣告型號**（`policy/MODEL_IDENTITY.md`）
2. 讀狀態文件（`NEXT_SESSION_MEMO.md`）
3. 讀 T0 兩份
4. 首次參與者加讀 `Incident_Log.md`
5. **複述自己的寫入範圍**（§6）
6. 跑 `run_all_sensors.py`，**確認退出碼**

### 4.2 收工

1. 跑 `run_all_sensors.py`
2. 覆寫狀態文件
3. **交出交接封包**（`policy/HANDOFF.md`）
4. 提出決策請求（§5）

⚠️ **凡本輪變更影響到他人的權限、規格或工具行為，一律須交封包並指名收件人**——
**包含治理／流程維護角色本身。**
先行專案曾長期由治理角色只寫自己的備忘而不交封包，
**結果是其他角色只會在下次違規時才發現規則變了。**

---

### 4.3 🔴 當工作指令與 T0 衝突時（**最容易被忽略的一條**）

**框架原本只有「決策請求」，那是用來提議修改規則的——
它沒有回答「此時此刻我該怎麼辦」。**

⚠️ **實測發現：** 受測 agent 收到「把猜想寫進台帳」的指令，
而四份文件都寫著「AI 不得寫入台帳」。
**它自己從豁免條款推導出處置方式並執行了。**

> **一個 agent 靠自己推導出「我可以破例」，本身就是這套框架最該擔心的事。**

**→ 明文處置，四選一，依序判斷：**

| 情形 | 處置 |
|---|---|
| 指令與 T0 的**硬禁止**（⛔ 條款）衝突 | ⛔ **停止並回報。不得執行。** |
| 指令與 T0 的**程序規定**衝突，且**不執行就無法完成任務** | ✅ 執行，**但須在產出物開頭登錄豁免**：豁免了哪一條、為什麼、代價是什麼 |
| 指令與 T0 衝突，但**有不衝突的替代做法** | ✅ **一律改走替代做法**，並回報你改了 |
| 無法判斷屬於哪一種 | ⛔ **停止並回報。** ⚠️ 「無法判斷」不得預設為可執行 |

⛔ **不得靜默執行。** 三種可執行的情形都要求你說出來。
**框架能容忍破例，不能容忍沒有人知道破過例。**

## 5. 決策請求標準格式

```
> **[裁決請求 N] <一行標題>**
> **當前變動：** 具體要改什麼
> **動機：** 為什麼現在要改
> **驗證狀態：** 我驗證了什麼、沒驗證什麼、殘餘風險是什麼
> **選項：** [A …]（建議）／[B …]／[C 不處理]
```

⛔ **「驗證狀態」欄不得為空，且不得寫「已充分驗證」。**

### 5.1 待裁決佇列須可見化

狀態文件中的待裁決清單**須含「已等待幾輪」欄**。

⚠️ **理由：** 主持人是唯一裁決點。當佇列成長速度超過消化速度，
**失效形態是「裁決品質下降」而非「裁決沒做」——那不會有任何紅燈。**
**等待輪數本身就是訊號。**

## 6. 寫入範圍

**依所選 profile 設定，登錄於 `file_index.md`。**

### 6.1 什麼是「產出區」

**產出區 ＝ 該角色本輪的工作成果應該落地的目錄。**

| 情境 | 產出區 |
|---|---|
| 單一 AI | 專案根目錄，**扣除**台帳、T0 與 `scripts/` |
| 多角色 | `framework_config.py` 的 `write_scopes` 所列 |

⛔ **無論哪一種情境，下列一律不在任何 AI 的產出區內：**
`ledgers/`（台帳）、`governance/AGENTS.md`、`governance/WORKFLOW_CONSTITUTION.md`

✅ **`NEXT_SESSION_MEMO.md` 是每個角色產出區的一部分**——
收工儀式要求覆寫它（§4.2），若不納入，**§4 與 §6 會互相牴觸**。
⚠️ 此項由框架自身的實測發現：受測 agent 因兩節牴觸而選擇不覆寫，
**該檔至今是三個空格。**

**三條通則：**

1. **一個角色只寫自己的產出區 ＋ `handoffs/`。**
2. ⛔ **台帳不在任何 AI 角色的寫入範圍內。**
3. **每個例外都要寫下它的代價。**
   ⚠️ 一個豁免是可以的，但**豁免應該是「看得見的」而不是「安靜的」**。

## 7. 感測器治理

### 7.1 變更三關（缺一不得提交）

① 成對種入缺陷樣本（**「必須抓到」＋「必須不誤報」**）
② `run_selftest.py` 全數通過
③ 於 `scripts/harness/SENSOR_CHANGELOG.md` 登錄觸發個案

### 7.2 「無實測個案不改」的適用範圍

| 對象 | 規則 |
|---|---|
| **感測器** | ⛔ **無實測個案不建。** 誤報會教人忽略感測器 |
| **文件規則** | ✅ 得依風險預先設立，**但須標 `[預測]` 並寫下複核時機** |

⚠️ **兩者的失效成本不對稱，所以判準不該相同：**
**一支誤報的感測器會被關掉，而一條沒被觸發的文件規則只是沒被觸發。**

### 7.3 查核工具誤報的處置

⚠️ **當一個查核工具宣告產物有缺陷時，先假設壞掉的是工具。**

| 步驟 | 動作 |
|---|---|
| 1 | **用第二個獨立工具複核** |
| 2 | 檢查比對兩側的**正規化是否完全對稱**。單側正規化＝自製假陽性 |
| 3 | 檢查正規化的**順序**：先剝結構，後壓縮 |
| 4 | 三步都通過，才可宣告產物有缺陷 |

⛔ **不得以「調鬆判準」作為誤報的處置**——那會同時關掉真陽性。
處置一律是修正比對邏輯，**並補一個「必須不誤報」的成對樣本**。

### 7.4 三個退出碼

| 碼 | 意思 |
|---|---|
| 0 | PASS |
| 1 | FAIL — **確定的缺陷** |
| 2 | **INCOMPLETE — 查不了。⛔ 這不等於通過** |

⚠️ **崩潰也算 INCOMPLETE，不算 FAIL。**
把兩者混為一談，會讓「感測器壞了」看起來像「文件有問題」——**而那會讓人去修一份沒問題的文件。**

### 7.5 治理變更的跨層檢查表

**每次治理變更前，逐層自問：這次動到哪一層？它會迫使哪一層跟著改？**

| 層 | 對應 |
|---|---|
| **E** 執行 | 沙盒邊界、暫存區 |
| **T** 工具 | `scripts/` |
| **C** 脈絡 | 文件分層、狀態文件、台帳 |
| **L** 生命週期 | 儀式、交接、決策請求 |
| **O** 可觀測 | git 檢查點、log、可重跑指令 |
| **V** 驗證 | 感測器、成對自測 |
| **G** 治理 | 寫入範圍、倫理閘門、語彙規則 |

⚠️ **實測：兩次跨層連鎖都不是事前想到的，是感測器當場擋下的**——
擴大語料庫寫入權 → 被迫新增雜湊檢查；給審計沙盒 → 立刻撞上 T0 唯一性。

## 8. 跨模型對抗審計

**規格見 `governance/Audit_Protocol.md`。本節只定四項不可省略者：**

1. 審計者**與被審者不得為同一模型**
2. 報告須含「**我測了什麼／我沒測什麼**」兩欄，**後者不得為空**
3. 結論的效力範圍**不得超出測試矩陣**
4. ⛔ **審計者不修東西**
