# 初始化指導說明書

**這份說明假設你沒有任何程式背景。**
全程大約 40 分鐘，其中 30 分鐘是你在回答關於自己研究的問題。

> ⚠️ **請照順序做，不要跳。**
> 第 5 步之前的每一步，都是為了讓第 5 步的檢查真的跑得起來。

---

## 步驟 0：先確認你需要的是這個

**適合你，如果——**

- 你有一個**還沒成形的研究構想**，想把它變成一份可以送出去的提案
- 你會用 AI 幫忙，但**最後由你負責**
- 你願意多花大約兩成的時間，換取「錯誤會留下痕跡」

**不適合你，如果——**

- 你要的是快速產出。**本框架會拖慢你，而那是刻意的**
- 你的工作裡沒有需要查證的事實
- ⛔ **你希望 AI 自己一路做完，你只看最後結果。** 本框架的假設剛好相反

---

## 步驟 1：取得框架資料夾（約 5 分鐘）

**這一步不需要 Git，也不需要任何指令。**

1. 到專案首頁 <https://github.com/yama-learns/Spark2Groundwork>
2. 按綠色的 **Code** 按鈕 → **Download ZIP**
3. 解壓縮下載回來的檔案
4. 裡面有兩個資料夾，**取走中文版那一個**：`Spark2Groundwork_zh`
5. **把它複製到你放工作檔案的地方，然後改名為你的專案名稱**，例如 `雙語記憶研究`
6. ⛔ **其餘下載回來的東西可以刪掉。** 你只需要那一個資料夾

⚠️ **從現在開始，「專案資料夾」指的就是你剛剛改名的那一個。**

## 步驟 2：安裝兩個程式（約 10 分鐘）

| 要裝什麼 | 為什麼 | 去哪裡下載 |
|---|---|---|
| **Python 3.9 以上** | 執行自動檢查 | <https://www.python.org/downloads/> ⚠️ **安裝畫面上請勾選「Add Python to PATH」** |
| **Git** | 記錄「AI 改了什麼」，讓你能逐行看 | <https://git-scm.com/downloads>（Mac 也可以用 `brew install git`） |

### 2.1 確認裝好了

打開終端機（**Windows**：在開始選單搜尋 `cmd`；**Mac**：搜尋「終端機」），
逐行輸入下面兩行，每輸入一行按一次 Enter：

```
git --version
python3 --version
```

**兩行都要印出版本號碼**，例如 `git version 2.45.0`。

⚠️ **Windows 上如果 `python3` 沒反應，改打 `python`。**
⚠️ **Mac 上如果 `python3` 沒反應**，先執行一次 `xcode-select --install`。

## 步驟 3：把資料夾交給你的 AI（約 5 分鐘）

**框架就是一堆檔案，所以任何讀得到你資料夾的 AI 都能用。**
以下是三種常見做法，步驟以本文撰寫時的介面為準。

### 3.1 Claude：用 Cowork

1. 打開 Claude 桌面版
2. 左側找到 **Projects**，按 **+**
3. 選 **Use an existing folder on your computer**（使用電腦上既有的資料夾）
4. 選你的專案資料夾，替專案取個名字，按 **Create**

之後 Claude 可以直接讀寫資料夾裡的檔案，也可以替你執行檢查。

### 3.2 Gemini：用 Antigravity

1. 打開 Antigravity
2. 按 **Select Project → New Project**
3. 用 **Add Folder** 把你的專案資料夾加進去，然後建立專案
4. 在主畫面直接跟 agent 對話。想用完整編輯器的話，按 **Open IDE**

一個 project 可以放不只一個資料夾，所以你可以把相關材料一起加進去。

### 3.3 ChatGPT：用桌面版的「工作」模式

1. 打開 ChatGPT 桌面版，切到上方的 **工作** 分頁
2. 按輸入框下方的 **選擇專案**，再按 **新增專案**
3. 在跳出的「**建立專案**」視窗裡，填「**專案名稱**」
4. 在「**來源資料夾**」底下，按那個寫著「**新增 ChatGPT 可讀取及編輯的資料夾**」的方塊，
   檔案總管會跳出來（視窗標題是 `Select Project Root`），**選你的專案資料夾**
5. 按「**建立專案**」

之後「工作」模式就能直接讀寫那個資料夾裡的檔案，而且連結會保留下來——
⛔ **你不需要每次重新上傳。**

⚠️ **能不能連結本機資料夾，取決於你的方案；在組織帳號下還取決於工作區設定。**
如果畫面上沒有出現連結資料夾的選項，原因通常是這個。

⚠️ **網頁版的 ChatGPT 是另一回事。** 那裡的「專案」放的是上傳的副本而不是即時資料夾，
而且有檔案數量上限（免費 5 個、Go／Plus 25 個、更高方案 40 個）。
還是能用，只是複製貼上的工作會比較多——
**你的資料夾裡有一份 `profiles/PROFILE_chat_only.md`，就是為那種情況寫的。**

### 3.4 你已經在用寫程式的 AI？

**Claude Code 與 ChatGPT 的 Codex 也能用這套框架**，而且它們最直接——
**它們本來就活在資料夾裡，讀檔、跑指令都是原生能力。**

⚠️ **我們沒有實測過這兩個，所以不寫步驟。**
照你平常的方式讓它讀到這個資料夾，然後從 `SETUP.md` 開始就可以了。

⛔ **不過有一件事要先知道：** 寫程式的 AI 會很順手地改檔案、跑指令，中間不會停下來問你。
🔴 **這套框架的保護來自「按快照」這個習慣**——派工前按一次、看完後按一次。
**⛔ 沒有任何東西會替你強制執行它。**

⚠️ **介面會改版。** 如果你看到的選單跟上面不一樣，
找意思相同的字：「加入資料夾」「連結資料夾」「專案指示」。

## 步驟 4：填空與放材料（約 20 分鐘，**這一步不能交給 AI**）

### 4.1 填 `PROJECT.md`

🔴 **這是你需要親筆填的兩份專案檔之一。**
另一份是同層的 `第一個想法.md`；其他治理文件都由 AI 維護，**你不需要打開它們。**

⚠️ **其中 §1.1 的三個問題必須你自己回答，⛔ 不可以請 AI 代答：**

> **① 如果這個問題得到答案，哪一個既有的說法會因此站不住？**
> （不能答「增進理解」「填補空白」。**要指名一個具體的受害者。**）
>
> **② 這件事是還沒有人回答，還是已經有人回答而我不知道？**
> （這是事實問題，查文獻就能回答，**不是拿形容詞帶過**。）
>
> **③ 為什麼是我要做這一題？**

**為什麼不能給 AI 代答：**
這三題是用來防止**研究題目被 AI 悄悄接管**的。
如果你答不出第三題，你正在做的很可能是「AI 覺得好做」的題目，而不是你想做的題目。

### 4.2 填 `第一個想法.md`

**打開專案根目錄、與 `PROJECT.md` 同層的 `第一個想法.md`，把最下方的佔位文字
換成你的完整構想。** 上方的拆解規則不要刪；AI 在第一輪會讀取整份檔案。

🔴 **這是專案專屬檔。** 它刻意不放在 `prompts/`：`prompts/` 是升級時可整包替換的
框架資料夾，而你的構想不可被升級覆蓋。

### 4.3 把論文放進 `corpus/`

**把你要引用的 PDF 全部放進 `corpus/` 資料夾。**
一篇一個檔，檔名建議寫成「第一作者_年份_關鍵詞.pdf」。

**為什麼一定要放進來：** 框架會檢查「你引用的那句話在不在原文裡」。
原文不在專案裡，這件事就查不了——⛔ **而查不了不等於沒問題。**

### 4.4 建立你的書目總表

`corpus/` 裡有一份 **`書目總表.docx`**，現在是空白的。

**請這樣做：**

1. 用 **Zotero** 或 **EndNote** 管理你讀過的文獻（兩者都有免費版）
2. 從它匯出整份書目，選你要的格式（APA、Chicago 等）
3. **把匯出的內容貼進 `書目總表.docx`**
4. 之後每次新增文獻，回來更新這一份

🔴 **從此本專案所有的引用格式，一律以這份檔案為準，⛔ 不以 AI 說的為準。**

⚠️ **為什麼要多做這一步：**
AI 給的 DOI、頁碼、年份會出錯，**而且錯得跟對的一模一樣。**
實測過的一個例子：某個模型列出八筆參考文獻，**篇篇都是該領域的正典文獻，
但至少三筆的識別碼是錯的。**

> **「這幾篇是不是好文獻」它答得出來；「這個 DOI 對不對」它答不出來——**
> **而這兩種回答，讀起來一樣有把握。**

⛔ **不要請 AI「幫你把 DOI 補上」。** 它會補，而且補得很像對的。
✅ **可以請 AI 做的是：** 拿你的書目總表去對它自己寫的引用，**把對不上的列出來給你。**

⚠️ 如果你之後讓 AI 直接連上 Zotero（例如透過連接工具），那也可以，
**但建議仍然保留這份檔案，當作離線時的對照本。**

### 4.5 建立第一個檢查點

**Windows：** 雙擊 `記錄快照.bat`
**Mac：** 雙擊 `記錄快照.command`

看到「已建立新的檢查點」就成功了。

⚠️ **Mac 第一次雙擊如果沒有反應**，在終端機裡執行一次：

```
chmod +x *.command
xattr -dr com.apple.quarantine .
```

（第二行是因為 macOS 會把從網路下載的檔案標記起來，執行過一次就好。）

## 步驟 5：選一份設定，跑第一次檢查（約 7 分鐘）

### 5.1 選設定

**打開 `profiles/` 資料夾，挑一份：**

| 你的情況 | 選這一份 |
|---|---|
| 只有你和一個 AI | `PROFILE_solo.md` |
| 多個 AI 分工（研究／治理／審計） | `PROFILE_multi_agent.md` |
| 沒有檔案存取，只有聊天視窗 | `PROFILE_chat_only.md` |
| 會用到 Deep Research、n8n 之類的外部工具 | 上面任選一份，再加 `PROFILE_external_tools.md` |

**每一份設定都會告訴你：哪些文件要留、哪些可以刪、要跑哪幾支檢查。**

⛔ **不要全部都留。**
一份沒有人維護的治理文件，比沒有那份文件更糟——**它會讓你以為有人在看。**

⚠️ **若你選了多角色設定：** 請在專案根目錄自己建一個叫 `scratch` 的資料夾，
**當作審計角色的沙盒。** ⛔ 它不隨框架附上——**`scratch/` 的定義就是「不進版本控制」。**

### 5.2 先跑自我測試

```
python3 scripts/harness/run_selftest.py
```

**應該看到「自測全數通過」。**

⚠️ **如果沒通過，先不要動檢查程式。**
自測失敗代表**檢查程式本身壞了，或你的環境有問題**，⛔ 不是你的文件有問題。
把完整輸出交給 AI，並明講「這是自測，不是專案檢查」。

### 5.3 再跑專案檢查

```
python3 scripts/harness/run_all_sensors.py
```

**新專案第一次跑會出現一批警告，那是正常的**——
你的台帳還是空的，程式在提醒你欄位沒填。

### 5.4 三種結果的意思

| 印出來的碼 | 意思 | 你該做什麼 |
|---|---|---|
| **0** | 通過 | 繼續 |
| **1** | 有缺陷 | **確定有問題。** 修好再繼續 |
| **2** | **查不了** | ⛔ **這不等於通過** |

⚠️ **第三個最重要。**
「查不了」的意思是檢查程式沒能完成檢查。
**把它當成通過，正是本框架最想擋掉的那一類錯誤。**

## 步驟 6：把構想交給 AI（約 5 分鐘）

**先確認 `第一個想法.md` 已填好，再把 `INITIALIZE_PROMPT.md` 的整份內容貼給能讀取
此專案資料夾的 AI。** AI 會直接讀取 `第一個想法.md`，不必再把構想複製進訊息。

那份指令會要求 AI：

1. 先讀治理文件，並**複述一次它可以寫哪些地方**
2. 把你的構想**拆成編號的猜想**，每一條都要附上「怎樣才算被推翻」
3. ⛔ **先不要開始查文獻**——**先讓你確認拆解對不對**

⚠️ **第 3 點是刻意的。**
如果一開始就拆錯了，後面查再多文獻，都只是在證明一個錯的東西。

## 步驟 7：之後每一輪怎麼跑

```
      ┌──────────────────────────────────────────────┐
      │  ① 按「記錄快照」        建立檢查點            │
      │  ② 跑 run_all_sensors.py  確認沒有紅字         │
      │  ③ 把任務交給 AI                               │
      │  ④ AI 收工，交出一份交接說明                    │
      │  ⑤ 按「查看變更」        看它到底改了什麼       │
      │  ⑥ 你做決定 → 更新台帳                         │
      │  ⑦ 再按一次「記錄快照」  ＝「我看過了」          │
      └──────────────────────────────────────────────┘
```

**三個按鈕就在專案資料夾最上層**（Windows 用 `.bat`，Mac 用 `.command`）：

| 按鈕 | 什麼時候按 |
|---|---|
| **記錄快照** | 派工之前，以及看完之後 |
| **查看變更** | AI 收工之後 |
| **檢查更新** | 偶爾按一次，看框架有沒有新版（步驟 9） |

⚠️ **第 ⑦ 步不是形式。**
它會把一個叫「已檢視」的標記往前移，**下一次的「改了什麼」就是從這裡開始算。**
不按的話，你下次會重複看到同樣的內容。

## 步驟 8：先跟你講幾件一定會遇到的事

### 8.1 檢查程式會誤報

**會。而且第一次誤報的時候，你會想把它關掉。**

⛔ **不要把判斷標準調鬆。**
正確的做法是修比對邏輯，並且**補上一個「這種情況不該報警」的測試樣本**。
`my/MY_RULES.md` 裡有完整說明（框架規則的副本在它的 §1）。

### 8.2 AI 會在最有把握的地方出錯

**兩個先行專案合計四十幾筆失誤，幾乎全部發生在當事者語氣最肯定的段落。**

→ 所以 `governance/Audit_Protocol.md` 要求：
**抽查你最確定的那幾條，不是最不確定的那幾條。**

### 8.3 你會想跳過台帳

**登錄一筆主張要填錨點和頁碼，比直接寫一句話慢五倍。**

⚠️ **而那正是它的用處：**
填頁碼會逼你真的去翻那一頁——**而翻到那一頁，你常常會發現它跟你以為的不一樣。**

## 步驟 9：框架有新版時怎麼升級

**按「檢查更新」按鈕**，它會告訴你手上是哪一版、GitHub 上最新是哪一版。

⚠️ **版本標記只回答「這個資料夾自稱哪一版」，不證明內容完整。** 把新版放進
`_upgrade/` 後再按一次，按鈕會自動接著做唯讀差異檢查；兩步都不會改檔案。

**要升級的話，三步：**

1. 到 GitHub 下載新版的 ZIP，解壓到專案裡的 `_upgrade/` 資料夾
2. 再按一次「檢查更新」——它會列出哪幾包跟你手上的不一樣
3. **一次換一包**，例如：
   ```
   python3 scripts/harness/upgrade.py apply governance
   ```

🔴 **它只會替換它認得的那幾樣東西**：
資料夾：`governance`、`profiles`、`prompts`、`scripts`、`docs`；
根目錄檔案：四份說明檔與各平台的啟動器。

⛔ **除此之外的一切都不會被碰**——
**包含 `PROJECT.md`、`第一個想法.md`、`ledgers/`、`corpus/`、`my/`，
也包含你自己開的任何資料夾**（筆記、圖表、投稿版本，隨你怎麼開）。

⚠️ **這一點值得講清楚，因為它常被誤解：**
**保護你的不是一份「受保護清單」，而是「可替換清單」。**
🔴 **工具只認得上面明列的那些名稱，其餘一律拒絕**——
**所以你不需要事先向誰登記你開了哪些資料夾。**

🔴 **即使名稱是可替換的框架資料夾，裡面若有新版來源沒有的檔案，程式也會先停止、
逐一列名；它不猜所有權，也不建立檢查點。** 先把專案檔移出去再重跑。

⚠️ **上述程式路線每次執行 `apply` 時，會在覆蓋前自動建立檢查點；檢查點失敗就不覆蓋。**
它也刻意沒有「全部一次換掉」的選項，必須一次換一包。

Windows 上的例行 `diff` 不會要求補齊缺少的 `.command`，macOS 也不會要求補 `.bat`。
**若你確實要製作跨平台專案，仍可用完整檔名明確執行 `apply`，例如
`upgrade.py apply 記錄快照.command`。** 這是刻意保留的明確操作，不是例行差異項目。

### 從 v1.4.2 或更早版本升級（兩條路徑都要做）

無論使用程式或下方的手動方式，都至少檢查四處：

1. 已填內容的 `prompts/TEMPLATE_decompose.txt` 搬到專案根目錄，改名為 `第一個想法.md`。
2. 放在 `scripts/` 的自建工具搬到 `my/tools/`；治理 AI 可依主持人授權維護該處。
3. 多 AI 專案人工檢查 `governance_config.json`：若主持人已授權治理角色維護專案規則、
   事故簿、索引說明與自建工具，其 `write_scopes` 必須包含 `my`。升級不會覆寫這份設定。
4. 🔴 **`policy/` 已於 v1.4.4 退役**，它的四份文件（`SOURCES.md`、`MODEL_IDENTITY.md`、
   `HANDOFF.md`、`EXTERNAL_TOOLS.md`）搬進了 `governance/`。
   **⛔ 新版沒有同名的 `policy/`，所以整包替換⛔ 不會碰到你的舊 `policy/`——它會原地留下。**
   → **先確認新版 `governance/` 裡確實有那四份**，再把舊 `policy/` 移出專案（或刪掉）。
   ⚠️ **⛔ 程式與框架都不會自動刪除它**；程式路線只會在 `check`／`diff`／每次成功的
   `apply` 之後把它列名。**⇒ 手動路線⛔ 沒有那個提醒，所以要在這裡自己記得。**

每次替換 `governance` 後，也要讓 `my/MY_RULES.md` 補齊新版公版規則：
執行 `python3 scripts/harness/tool_sync_my_rules.py`。
**它會把缺少的條目逐字附加，⛔ 而且永遠不會覆蓋你檔案裡任何一個既有的字。**

若完全不執行程式碼，就從新版 `governance/RULES.md` 逐字複製缺少的 `R-xx` 條目，
貼在 `MY_RULES.md` 的 `FRAMEWORK_RULES_END` 註解之前。
**不得整份取代 `MY_RULES.md`，否則專案規則與覆寫會消失。**

#### 🔴 v1.4.4 修訂了 `R-34`，這一項需要你動手

**本版是本框架第一次修訂一條「已經發布出去」的規則。**
⚠️ **⇒ 你的 `my/MY_RULES.md` 裡那一條會與新版不同，感測器會報 `RULE_TEXT_DRIFT`。**

**規定動作：**

1. 跑 `python3 scripts/harness/tool_sync_my_rules.py`
2. 它會印出**逐行差異**，`+` 開頭的就是新增的句子
3. **把那幾行逐字貼進 `my/MY_RULES.md` 裡 `R-34` 的正文**
4. 再跑一次，確認漂移消失

⛔ **⛔ 沒有工具會替你做第 3 步，這是刻意的。**
🔴 **一支會自動覆寫使用者規則檔的工具，在本版的覆核中被發現會在檢查點失敗時仍然寫入——
⇒ 整個寫入路徑已被退回。** ⚠️ **一份看得懂的差異，比一個省下十秒的自動覆寫值得。**

⚠️ **如果那一條是你刻意改過的**（而不是框架改的），
就在該條正文另起一行標 `[本專案覆寫]` 並寫下理由——⛔ 那樣感測器就不會再報它。

#### 🔴 v1.4.4 另有一項需要你動手：檢查 `reviewed` 基準

**v1.4.1 與 v1.4.2 有一個缺陷：`upgrade.py apply` 會把 `reviewed` 標籤
移到升級前的那一個提交，並印「人工檢查點：我看過了」——⛔ 而你並沒有按下那個按鈕。**

🔴 **後果⛔ 不是標籤變了，是「查看變更」的基準被往前推：**
**如果升級當下有 AI 做完、而你還沒審閱的工作，那些變更會從「上次我看過之後動了什麼」裡消失。**

⚠️ **v1.4.4 已經修好（升級工具現在以 `--mode tool` 呼叫，⛔ 而 `tool` 與 `ai` 都不動那個標籤）。**
⛔ **但已經被移動過的標籤，程式修好也不會自己還原**——**⇒ 這一項只能你來判斷。**

**怎麼查——三步，⛔ 而「查不出來」本身也是一個結論：**

**第 1 步：看標籤現在停在哪一種提交上**

```
git log --oneline -1 reviewed
```

| 訊息開頭 | 這代表什麼 |
|---|---|
| `snapshot …` | 人工檢查點的提交。⚠️ **可能是你按的，也可能是升級替你按的**——往第 2 步 |
| `auto: …` | AI 自己存的提交。⚠️ **這⛔ 不證明有問題**：你在 AI 做完之後按一次「記錄快照」，標籤本來就會落在這裡——往第 2 步 |
| `tool: …` | v1.4.4 之後的工具還原點。🔴 **這一定有問題**：`tool` 模式⛔ 不移動標籤，⇒ 標籤⛔ 不可能自己走到這裡 |
| 其他（`release:`、你自己下的 commit……） | ⚠️ 這一步判不出來——往第 2 步 |

🔴 **⛔ 不要把「訊息開頭」當成唯一判準。**
⚠️ **上表第二列就是理由：`auto:` 既是這個缺陷的結果，也是正常流程的結果，⛔ 兩者長得一模一樣。**
**⚠️ 而在乾淨工作區升級時（最常見的情形），舊版升級留下的正是這一種。**

**第 2 步：查 `git-checkpoint.log`**

```
grep -n "mode=human" git-checkpoint.log        # macOS／Linux
Select-String "mode=human" git-checkpoint.log  # Windows PowerShell
```

**每一筆都有 UTC 時間。把它們與「你自己記得按過按鈕」對一次：**

- **有一筆 `mode=human` 的時間，剛好落在你執行升級的那一刻，而你當時並沒有按按鈕**
  → 🔴 **那一筆就是升級偽造的，⇒ 標籤現在的位置不可信。**
- **`git-checkpoint.log` 不存在**（它⛔ 不隨框架包發布，是你的專案自己長出來的）
  → 這條路走不通，往第 3 步。

⚠️ **⛔ 不要去找「標籤何時被誰移動」的紀錄——Git ⛔ 沒有替這種標籤保留 reflog**
（`core.logAllRefUpdates` 預設只涵蓋分支、遠端與 notes）。**⚠️ 寫在這裡，免得你去找一個不存在的東西。**

**第 3 步：兩步都判不出來的時候**

🔴 **⛔ 不要猜，⛔ 也不要「先重設看看」。**
**保守做法是把基準往回退到一個你確定看過的位置，再重看一次：**

```
git log --oneline -30                 # 這段歷史長什麼樣
git diff <你確定看過的那個提交>          # 從那裡到現在的全部差異
```

⚠️ **代價是你會重看一些已經看過的東西。**
🔴 **⛔ 而反方向的代價是「有一段你沒看過的東西，從此不再出現在任何清單上」——⛔ 那個不可逆。**

⛔ **這一段⛔ 不要用「查看變更」按鈕做**——
**那個按鈕的基準就是 `reviewed`，⛔ 而 `reviewed` 正是你現在懷疑的東西。**

**判斷完之後，兩種處置，選一個：**

| | 做法 | 什麼時候選它 |
|---|---|---|
| **[A]** | **用上面第 3 步的 `git diff <確定看過的提交>` 重看一次，然後按「記錄快照」** | 🔴 **建議。** 你會看到從那個安全基準到現在的全部變更，看完才把基準往前推 |
| [B] | `git tag -f reviewed <你確定看過的那個提交>` | ⚠️ 你清楚記得自己審到哪裡；⛔ **只把基準往回退，不得往前推** |

⛔ **⛔ 不建議放著不管**——**一個指向你沒看過的地方的「我看過了」，
比沒有標籤更糟：沒有標籤時「查看變更」會拿 `HEAD` 當基準並明說，⚠️ 而錯的標籤不會說。**

### 9.1 不執行程式碼的整包替換

你也可以完全不跑升級工具：先備份整個專案，再逐包把舊框架資料夾移走、放入新版
同名資料夾。**但在移走前，必須先把其中的專案專屬檔搬出去。**

`governance_config.json`、`my/`、`PROJECT.md`、`第一個想法.md`、台帳與語料都留在原位，
不得隨框架包替換。Windows 專案可以只保留 `.bat`；macOS 專案可以只保留 `.command`。

🔴 **⚠️ 手動路線有一個陷阱，是「同名資料夾」這個做法本身造成的：**
**一個在新版已經退役的資料夾，⛔ 不會有同名的新版可以換進去**——
**⇒ 它會安靜地留在你的專案裡，而它看起來仍然像框架的一部分。**
**⛔ 上面「從 v1.4.2 或更早版本升級」的第 4 項就是這種情形，⚠️ 每一次升級都要回頭看那一節。**

⚠️ **這條手動路徑不會自動建立檢查點，也沒有程式替你阻止一次換多包。**
前面的整份專案備份就是復原來源；仍建議一次換一包、每包替換後先檢查再繼續。

## 附：常見問題

**Q：我可以只用其中一部分嗎？**
可以，`profiles/` 就是為此而設。
**但建議至少保留主張台帳和 Git 檢查點**——這兩樣的成本最低、回報最高。

**Q：AI 可以自己更新台帳嗎？**
⛔ **不建議。** 台帳記的是「你確認過什麼」。
AI 直接寫進去，就沒有人在確認了。
正確做法是：AI 用「請你裁決」的格式回報 → 你決定 → 再寫進去。

**Q：我不會用 Git，一定要學嗎？**
**那三個按鈕就是為了讓你不必學。**
你只要記得兩件事：**派工前按一次、看完後按一次。**

**Q：這套東西會不會太重？**
如果你全部都用，會。**這正是 `profiles/` 存在的理由。**
⚠️ 另外請注意：**框架自己就有一條規則在防「治理文件愈長愈多」**——
它假設文件會膨脹，⛔ 而不是假設你會自己克制。

**Q：我的論文 PDF 會被上傳到哪裡去嗎？**
⛔ **不會。** 所有檔案都留在你自己的電腦上。
**唯一的例外是你自己主動貼給 AI 的內容**——那要看你用的是哪一家 AI，
請自己確認他們的資料政策。
