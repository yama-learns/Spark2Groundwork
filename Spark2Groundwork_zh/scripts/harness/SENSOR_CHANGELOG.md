# 感測器變更記錄

**⛔ 每一次感測器變更都要在這裡登錄觸發個案**（憲章 §7.1 第三關）。

**格式：** 編號｜日期｜一句話。內容須含：觸發個案、修了什麼、成對樣本在哪。

> 🔴 **本檔有兩套 `#n`，共用一個命名空間。**
> **前史條目無日期；維護期條目一律帶日期。**
> ⛔ **引用維護期條目時必須連日期一起寫**（例：`#12 ｜ 2026-08-20`）；
> **引用前史條目寫「前史 #n」。⛔ 只寫 `#1` 是有歧義的。**
> ⚠️ **本檔為只增不改寫，⛔ 因此不重編號**——**改的是引用方式，不是紀錄本身。**
> ⚠️ **前史條目為各版本各自的歷史，⛔ 兩版不必一致**（英文版多一則英文版特有的常數問題）。

## #1 ｜ 框架自身的 solo agent 實測（**11 項缺陷，全部由受測 agent 發現**）

**方法：** 派一個獨立 agent 在框架副本中執行完整流程（讀規則 → 拆解一段跨領域散文 →
填空 → 跑感測器 → 交封包），並額外回答四個回饋問題。

### 🔴 最嚴重：框架自己的模板，教人寫出一種會關掉框架自己感測器的寫法

`TEMPLATE_decompose.txt` 第 3 條原本建議：反證條件填不出來時「標記為『反證條件待填』」。

**實測：照做之後，`FALSIFICATION_EMPTY` 由 2 筆掉到 1 筆，退出碼仍為 0。**
原因：感測器的 `PLACEHOLDERS` 只認完全相符的字串，
**「反證條件待填」被當成已填。**

⚠️ **這是「靜默過濾」家族，而觸發它的是框架自己的模板。**

### 🔴 更深一層：獎懲方向是反的

受測 agent 的原話：

> 留「—」看起來像我做得比較少；而編一句「若表徵相似性分析達 r > .8 則本條被推翻」
> 讀起來完全合格，**沒有任何人、任何感測器分得出來那是裝飾品**。
> 它甚至會讓那一條從 WARN 變成無警。
> **這條規則的獎懲方向是反的：誠實填「—」會亮黃燈，唬爛不會。**

**修正：告警條件由「欄位為空」改為「尚未經人裁決」。**
新增 `反證條件裁決` 欄位，**填了字不會讓警示消失，只有人改成 `已裁決` 才會。**
⛔ AI 不得自行改該欄。
**檢查碼由 `FALSIFICATION_EMPTY` 更名為 `FALSIFICATION_UNADJUDICATED`。**
成對 fixture：`conj_filled_unadjudicated`（填了字仍須告警）＋ `conj_clean`（已裁決不誤報）。

受測 agent 收到「把猜想寫進台帳」的指令，而**四份文件都寫著 AI 不得寫入台帳**。
它自己從豁免條款推導出處置方式並執行了，並登記了豁免。

> **一個 agent 靠自己推導出「我可以破例」，本身就是這套框架最該擔心的事。**

**框架能容忍破例，不能容忍沒有人知道破過例。**

### ✅ 兩項證明框架有效的觀察

1. **受測 agent 對七筆 WARN 逐筆判定，一筆都沒有為了讓畫面變綠而改文件。**
2. `Incident_Log` 的失效家族表起了作用——受測 agent 的原話：
   **「我是靠『靜默過濾』這個名字才認出模板與感測器的那個缺陷是什麼形狀的。」**

### ⛔ 本次測試無法驗證的事（**測試涵蓋範圍聲明**）

- **受測 agent 與框架作者是同一模型家族。** 跨模型對抗審計那一層**完全未受測**。
- 單輪測試。跨輪次的漂移（「索引當權威」「修一層漏另一層」「文件增生」三族）**未受測**。
- 未測外部工具情境、多角色情境、Windows 批次檔。

## #1 ｜ 2026-08-19 ｜ 提取工具：後端可辨識 ＋ manifest 自檢命中率

## #2 ｜ 2026-08-19 ｜ 自測：「不得誤報」那一半不再只驗退出碼

**觸發個案（他專案實測 → 本框架實查確認同樣成立）：**

`WARN` 級 finding **不改變退出碼**（`_common.py` 的 `emit`：只有 FAIL→1、INCOMPLETE→2）。
於是「不得誤報」測試若只斷言 `exit == 0`，**對任意多筆 WARN 級誤報一律印 ✅。**

**本框架修正前的實查（可重跑）：**

```

python3 scripts/harness/sensor_governance_text.py   --root scripts/harness/selftest/gov_clean
```

### 🔴 移植過程挖出的五個缺陷（**全部在中文版原始碼裡**）

| # | 缺陷 | 形狀 |
|---|---|---|
| 1 | `VALID_STATUS` 只有 🔵🟡🟢🔴 **四種**，而台帳 §0.1 定義**六種** | **一筆正確除役（⚫）或休眠（🟤）的猜想會被判 FAIL**——`R-19` 明文禁止的假陽性 |
| 2 | 反證條件檢查**沒有為 ⚫🟤 設豁免** | ⚠️ **與 1 互相遮蔽**：舊碼在狀態不合法時 `continue`，所以 ⚫🟤 從來走不到這裡。**只修一個會讓另一個當場現形** |
| 3 | 檔內硬編一份 `EXCLUDED_DIRS`，把 `import excluded` 蓋掉 | 與 `framework_config` 重複且**已不同步**（少 `node_modules`、`.venv`），且含一個**另一個專案的資料夾名**。違反憲章 §3.2 與 `R-21` |
| 4 | 台帳自我排除寫 `p.name != LEDGER_NAME`，而 `LEDGER_NAME` 是**路徑** | 永遠不等於裸檔名 → **台帳一直在掃描範圍內，`SCAN_GLOB_MATCHES_NOTHING` 永遠不可能觸發**。一個觸發不了的閘門與死豁免同型 |
| 5 | 掃描落空判 `FAIL` | 「掃不到」是**查不了**，應為 INCOMPLETE（`R-22`、憲章 §7.4） |

### 裁決 9 一併落地：刻意留白 ≠ 忘記填

台帳 §0.3 第 1 條逐字寫著「填『—』不會比亂填更糟，這是刻意設計的」，
而拆解模板第 3 條教人「反證條件填『—』，另在下一行寫 `**填不出來的理由：**`」——
**舊訊息對這種填法印的是「反證條件為空」，與忘記填一字不差。**

> ⚠️ **後果很難察覺：下一輪的人看到「為空」，很可能就去把它填上，
> 而那正是 §0.3 第 1 條想擋的行為。**

→ 新增 `FALSIFICATION_DECLARED_UNFALSIFIABLE`。
⚠️ **欄位名取自模板既有措辭**（zh `填不出來的理由`／en `Why I could not fill this`）——
⛔ 首版我在英文版自創了 `Why it cannot be stated`，**與模板不同步；已改正。
那正是憲章 §3.2 新增的「欄位名同樣是規則」在管的事。**

## #4 ｜ 2026-08-19 ｜ 自我背書感測器的少報，與 `deny` 鍵（裁決 2）

### 4a. 🔴 自我背書感測器對一份真實審計報告判 PASS

**觸發個案（`[實測]`，標本來自另一個實際運行的專案）：**
一份跨模型 Git 系統審計報告，結論寫著：

| 該報告的用詞 | `governance/Audit_Protocol.md` §3 |
|---|---|
| 「具備**極高**的強健性」 | ⛔ 禁用「極高」 |
| 「已經**堵死**了多數邊緣失效」 | ⛔ 禁用「堵死」 |
| 「**無待修復**的重大漏洞」 | ⛔ 禁用「無待修復」；且 §2.1 逐字以此為 ❌ 範例 |
| 「運作**完美**」×2、「**非常強健**」 | ⛔ 禁用 |

**而本感測器判 PASS。**

**根因不是 APPRAISAL 沒抓到**（極高／堵死／無待修復三個都在裡面），
**是 `SELF` 不含審計報告實際使用的自我指涉詞**——「本輪」「本次」「本專案」（無「已」）。
共現條件因此不成立。

> ⛔ **少報比誤報危險：一個誤報會被追查，一個少報不會。**

### 4b. ⚠️ 但放寬 `SELF` 會誤報「誠實揭露」——所以只放寬 WARN 分支

實測：「本輪未完成的項目**全部**列在 §3，其中兩項尚未**查證**」
會同時命中 `SELF(本輪)` ＋ `SCOPE(全部)` ＋ `OBJECT(查證)`，
**而那是一句誠實的揭露，不是背書。**
⛔ 誤報一條誠實揭露正是 `R-19` 要擋的——**它會教人不要寫「我沒做完什麼」。**

## #8 ｜ 2026-08-19 ｜ 裁決 21：猜想感測器改用共用的 `cli`／`emit`

**觸發個案：** `sensor_conjecture_ledger.py`（中文版）**自己帶了一份 `argparse` 與一份 `emit()`**，
與 `_common.py` 的那份平行存在。六支感測器裡只有它是這樣。

**後果不是輸出錯，是規則有兩個定義處：**

| 東西 | 定義處 A | 定義處 B |
|---|---|---|
| `--root`／`--json` 介面 | `_common.cli()` | 本檔自己的 `argparse` |
| 退出碼語意（0／1／2） | `_common.emit()`（憲章 §7.4） | 本檔自己的 `emit()` |
| JSON 輸出格式 | `_common.emit()` | 本檔自己的 `json.dumps` |

⚠️ **憲章 §3.2 管的就是這件事。** 兩份實作今天一致，**不代表下一個人改其中一份時也會一致**——
而改錯的那一次不會有任何訊息。

### ⛔ 我對這一項的預測是錯的，記在這裡

提請裁決時我寫的理由是「本檔的 `emit()` 收一個**獨立的 `incomplete` 布林參數**，
而獨立布林與 findings 可能不一致」。
**實查後不成立：舊碼寫的是 `incomplete = incomplete or any(f[0] == "INCOMPLETE" for f in findings)`，
它一樣從 findings 導出。**

> ⚠️ **一個看起來很像既有失效家族的形狀，不等於它就是那個家族。**
> 我是在動手前才去讀那一行的；**如果順序反過來，這份記錄會寫著一個不存在的缺陷，
> 而且讀起來完全合理。**

### 🔴 追記（2026-08-27，主持人跑了診斷之後）：**原因已確定，⛔ 不再是「未明」**

```
python -c "...capture_output=True, text=True..."
→ Exception in thread Thread-1 (_readerthread):
  UnicodeDecodeError: 'cp950' codec can't decode byte 0x94 in position 16

```

**Python 3.14.2、繁體中文 Windows。`text=True` 而⛔ 沒有指定 `encoding`，

**解碼發生在 `subprocess` 的讀取執行緒。⚠️ 那個執行緒死掉，例外⛔ 不會傳到主執行緒，
`communicate()` 回 `None`——於是呼叫端看到的是「exit 0，而且沒有輸出」。**
**⛔ 標準函式庫本身把一個錯誤變成了一個「安靜的空值」。**

### ⚠️ 這是同一個修法只做了一半

**`checkpoint.py` 與 `review_changes.py` 的 `run()` 逐字寫著
`encoding="utf-8", errors="replace"`——⛔ 而 `sensor_scope_and_t0.py` 沒有。**
🔴 **修法早就存在於同一個資料夾裡的兩支程式中，只是沒有被套到第三支。**

⚠️ **也是 `R-34` 的形狀：`_common._force_utf8()` 修的是「我們自己印出去的東西」，
⛔ 而它被讀成「編碼問題都處理過了」。⛔ 一個為真的修正，效力範圍不涵蓋另一條通道。**
**已在 `_force_utf8` 的說明裡補上它⛔ 不涵蓋什麼。**

### 追加的成對樣本

**`subprocess_encoding_case()`：以 `ast` 掃 `scripts/harness/*.py`，
凡 `subprocess.run` 帶 `text=`／`universal_newlines=` 而⛔ 沒帶 `encoding=` 者，一律 FAIL 並指名 `檔名:行號`。**

⚠️ **⛔ 這是靜態檢查，⛔ 不執行任何東西。理由：這個缺陷只在非 UTF-8 地區的機器上發生，
🔴 而一個「在我的機器上測不出來」的判準等於沒有判準。**

**實測：把 `encoding` 拿掉之後，自測當場報
`❌ 有 subprocess.run 會用系統地區編碼解碼：sensor_scope_and_t0.py:83`。**

**自測 71 → 72 項。**

## #20 ｜ 2026-08-27 ｜ 🔴 框架取代掉了使用者原本就有的索引

**觸發個案（主持人提供）：某專案套用 v1.3.0 之後，就不再維護自己的檔案索引了——
它的 `file_index.md` 裡⛔ 沒有一條跟研究有關。**

**機制：`file_index.md` 原本是先行專案用來管「研究計畫版本與輔助文件」的表。
在精煉為框架時，它的內容全部變成框架自己的東西，⛔ 而名字沒有換。**
🔴 **於是新使用者看到一份叫「檔案索引」的檔，以為那就是自己的索引——
然後他要嘛把自己的文件登記進去（升級時消失），要嘛就不再登記（實際發生的）。**

⚠️ **同一個專案的交接封包裡還有一句佐證：他刻意⛔ 不把自己寫的工具登記進 `file_index.md`，
理由是「升級時會被覆蓋，登記進去等於把指標放在一個會消失的地方」。**
**⇒ ⛔ 框架不只是忽略了使用者的索引，它取代掉了一個本來存在的機制。**

**新增：`tool_my_index.py`（產生器）＋ `sensor_my_index.py`（守望者）。**

### 三個設計判斷

**① 判準是「框架⛔ 不擁有的每一樣東西」，⛔ 不是一份要收哪些的清單。**
🔴 **一份要收哪些的清單就是白名單（`R-21`）：使用者永遠會發明新的資料夾。**
⚠️ **先行專案的產生器就是那個形狀，而它的作者自己寫下了那句話：
「手寫目錄會漏檔案，⛔ 而產生器會漏目錄。」**
**框架擁有哪些名字，唯一定義處是 `upgrade.py` 的可替換清單——⛔ 本工具 `import` 它，不另寫一份。**

**② 檔案清單由程式產生，說明由 AI 維護，兩者分開存放。**
⚠️ **主持人的實務：研究索引的說明一直是由研究 AI 維護的。
⛔ 而程式對 `.docx`／`.pdf`／`.xlsx` 取不到任何有意義的標題。**
🔴 **沒有說明的檔案⛔ 不會被藏起來，它們有自己的一段**——
**一份看起來完整而漏掉一半檔案的索引，比沒有索引更糟。**

**③ 感測器⛔ 不重寫產生邏輯，它呼叫 `tool_my_index.render()` 再逐字比對。**
⚠️ **兩份產生邏輯只要有一處不同，「是否過期」就會永遠說過期，
⛔ 而真正的原因是兩支程式不一樣。**

### 🔴 這支工具第一次執行就抓到另一個缺陷

**它列出「框架不擁有的東西」，而 `docs/`（兩張說明圖）與六個啟動器按鈕出現在那份清單裡。**
🔴 **⇒ 它們一直是框架的，⛔ 卻不在 `upgrade.py` 的可替換清單上——
意思是：v1.3.0 修好的七處說明圖跑版，⛔ 送不到任何一個既有專案。**
**已把 `docs` 與六個啟動器補進可替換清單。**

⚠️ **`.gitignore` 與 `.gitattributes` 刻意⛔ 不補**——它們是混合所有權（框架給預設值、
使用者往下加），依憲章 §6.4 整包替換會刪掉使用者加的那幾行。
**⛔ 已知代價已寫在 `upgrade.py` 的註解裡。**

### 成對樣本（**六項**）

| 樣本 | 必須 |
|---|---|
| 索引還沒產生過 | **INCOMPLETE**，⛔ 不是 PASS |
| 剛產生的索引 | ⛔ 不得誤報 |
| 🔴 **使用者自己開一個 `deepresearch/`** | **那個檔必須出現在索引裡**（⛔ 證明不是白名單） |
| 產生之後又多了一個檔 | **FAIL `MY_INDEX_STALE`** |
| 說明指向不存在的檔案 | **FAIL `INDEX_NOTE_DANGLING`** |
| 說明檔壞掉 | **INCOMPLETE**，⛔ 不得當成「沒有說明」 |

⚠️ **第三項的判準被自測當場改過一次：首版查的是「感測器的輸出」，
⛔ 而感測器只印統計、不印檔案清單。判準改為查產生出來的索引檔本身。**
🔴 **⛔ 那是我把判準對錯了對象，⚠️ 而自測抓到了它。**

**自測 72 → 78 項。感測器 8 → 9 支。**

## #21 ｜ 2026-08-28 ｜ 🔴 一支感測器報的是「你的作業系統不一樣」

**觸發個案：v1.4.1 發布當下。主持人跑步驟 2，`sensor_my_index.py` 報 `MY_INDEX_STALE`。
他手動跑了一次 `tool_my_index.py`，就變綠了。**

**⚠️ 主持人的回報值得逐字記下來：「我不知道這樣會不會有問題，所以還是跟你說一聲。」**
🔴 **那句話正是這一則存在的理由——他被一個假警報逼著在發布途中做了一個他不確定的動作。**

### 原因

**`tool_my_index.py` 舊版寫的是 `sorted(root.rglob("*"))`——⛔ 排的是 `Path` 物件。**
**⚠️ `WindowsPath` 的比較會先 casefold，`PosixPath` ⛔ 不會。**

| | Linux | Windows |
|---|---|---|
| `PROJECT.md` vs `corpus/` | `P`(0x50) < `c`(0x63) → **前面** | casefold 後 `project` > `corpus` → **後面** |

🔴 **我在 Linux 產生索引、隨 v1.4.1 一起發布，於是它在 Windows 上必然報過期。**
**⛔ 它報的⛔ 不是「索引過期」，是「你的作業系統跟產生它的那台不一樣」。**

⚠️ **這是 `R-19` 的教科書形態：一個對正確狀態報警的判準。**
**⛔ 而它的實際後果已經發生了——主持人繞過它，然後不確定自己有沒有做錯事。**

### 修了什麼

**排序的鍵改成「相對路徑的 posix 字串」。⛔ 不排 `Path` 物件。**
**Python 的 `str` 排序在兩個平台上都是碼點順序，⛔ 沒有平台差異。**

### 成對樣本

**`index_order_case()`：樣本裡放 `Zed.md` 與 `apple/x.md`
（`Z` 0x5A < `a` 0x61，⛔ 而 casefold 後 `apple` 在前），
斷言索引裡 `Zed.md` 出現在 `apple/x.md` 之前。**

⚠️ **⛔ 要誠實說它的效力範圍：這一項只在「檔名不分大小寫」的平台上會亮。**
**⛔ 在 Linux 上，舊寫法與新寫法的結果相同，所以它抓不到。**
🔴 **保留它的理由是：發布程序的第一步就在 Windows 上跑自測——
⚠️ 那正是這個缺陷唯一會現形的地方。**

⚠️ **⛔ 本框架不宣稱已經掃過同一形狀的其他地方**——
**「對一個排序行為跟平台有關的型別呼叫 `sorted()`」⛔ 沒有被盤點過。**

**自測 78 → 79 項。**
